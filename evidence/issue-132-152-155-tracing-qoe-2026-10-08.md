### #152 — Media-session correlation and sample lifecycle

The server `/voice/screen-metrics` path now accepts an optional `voice_lease_id`
handle in the OpenAPI contract. When present, it revalidates the canonical UUID
through the existing active voice-lease repository using the authenticated
account and session digest. Only after that lookup succeeds does the server
derive the compact `app.media.session.id` trace attribute. The client does not
choose the trace attribute, inactive or mismatched leases are rejected, and
the ID is not added to the public latest-sample aggregate or Prometheus labels.
Web and Flutter retain the server-issued lease handle with their telemetry
session and include it in screen reports; focused transport tests assert this
behavior. Reports without a lease handle retain legacy acceptance and have no
media-session correlation.

This safely links a server-reported measurement to its authenticated active
voice lease. It does not implement the issue's separate per-view launch or
generation binding, nor verified sender-to-receiver publication matching. Do
not treat the lease-level key as proof that two reports belong to the same
screen view, remote publication, or media-quality outcome.

Acceptance still needs two senders/two receivers, late callback across media
replacement, explicit first-frame/reconnect/recovery windows, and comparison of
sender/receiver records in the same authorized media-session drilldown. Tests
must additionally verify lease expiry/revocation during report submission,
room transfer, reconnect lifecycle, and isolation between concurrent viewers.
No live sender-to-receiver pairing or physical media-quality claim is made here.
