### #152 — Media-session correlation and sample lifecycle

Web and Flutter client `media.sample` source attaches visit, flow, and a
client-owned media-session ID. Its owner snapshot is checked before sample
emission; stale owner/media samples are dropped. The generated v1 schema and
relay validate the optional media-session ID. Dashboard source has a matching
media-session filter. The authenticated server `/voice/screen-metrics` path
also records numeric samples, but its `media.sample` trace is a separate root
with authenticated account/session only: the request contract currently has no
verified association to the client media session/view generation. Do not treat
that server copy as correlated with the client flow. Adding client-supplied IDs
to it without a server-verifiable media-context binding would overstate trust.

Acceptance still needs two senders/two receivers, late callback across media
replacement, explicit first-frame/reconnect/recovery windows, and comparison of
sender/receiver records in the same authorized media-session drilldown. No live
sender-to-receiver pairing or physical media-quality claim is made here.
