# API and realtime rules

All REST paths begin `/api/v1`; JSON responses use UTF-8. Errors have the stable shape `{ "error": { "code": "...", "message": "...", "request_id": "..." } }`. User-facing messages are Russian; error codes remain stable ASCII identifiers. Authentication is a secure HTTP-only cookie, not an authorization token exposed to browser storage.

The API generates a new UUIDv4 `X-Request-ID` for every response and places the same value in an error envelope; it never trusts a client-provided correlation ID. Every `POST`, `PUT`, `PATCH` or `DELETE` must carry an `Origin` exactly equal to configured `PUBLIC_ORIGIN`; other origins and missing Origin are rejected before a command handler executes. Production config must use the public HTTPS origin; `http://localhost:8088` in `.env.example` is local-only.

Registration and login use independent, bounded per-source fixed-window limits. A rejected command receives `429 RATE_LIMITED` and `Retry-After`; rate-limit keys remain process-local and are never emitted as public metric labels. Current parameters and Caddy ingress assumptions are in `docs/adr/ADR-003-auth-rate-limits.md`.

`GET /api/v1/health` is unauthenticated and returns `{ "status": "ok" }`. It is a process liveness signal, not proof that media, database migrations or capacity gates have passed.

`GET /api/v1/maintenance` is unauthenticated, uncacheable and returns only `{ "active": boolean }`. During a trusted release, a server-local command activates this state before migrations and disables it only after proxy validation and public health pass. While active, registration, login, new voice leases and private `/rtc` signal admission return `503 MAINTENANCE`; existing sessions, logout, protected reads and an already established media connection are not synthetically closed by this gate. The public response and banner expose neither deployment schedule nor operator identity.

`POST /api/v1/auth/register` accepts only `login` and `password`, creates a `MEMBER` account and returns public account fields without an authenticated session. `POST /api/v1/auth/login` accepts the same input and responds `204` with a secure, HTTP-only, same-site opaque session cookie; it never puts the raw session token or password hash in JSON. Invalid and unknown credentials share `UNAUTHENTICATED`; a blocked account returns `ACCOUNT_BLOCKED`.

`POST /api/v1/auth/logout` accepts no body. It derives a digest from the current session cookie, then serializes that account's voice state and atomically revokes both the current server-side session and every active logical lease issued from it. The same SQL statement writes a durable SFU revocation row for every revoked lease. It clears the cookie only after a successful revoke. A missing or malformed cookie is an idempotent `204`; a database failure is not falsely reported as a successful logout. The worker attempts private participant removal while the signal guard immediately denies a reconnect; POC-03 must still prove the connected-media and old-token outcomes.

`POST /api/v1/auth/password-reset/complete` accepts an opaque one-use reset secret and a replacement password. The browser obtains the secret from a URL fragment and sends it in the JSON body; it must never appear in a query string, request log or telemetry. The API stores and consumes only the SHA-256 digest. A single SQL command marks an unexpired unused reset consumed, updates the Argon2id password hash, revokes every active session and active logical voice lease for that user, and records the metadata-only application audit event. Malformed, expired, used and unknown resets share the same validation response; completing a reset never unblocks an account.

`POST /api/v1/admin/password-reset-links` requires a current `ADMINISTRATOR` session and accepts the target `account_id`. It returns a single-use URL in the one successful response, with the secret following `#token=` rather than in a query string. The API does not persist the URL or raw secret; the atomic creation command records only actor ID, target ID and event type. The current link-creation command is protected now; administrator bootstrap and complete account-management UI are separate capabilities.

`PATCH /api/v1/admin/accounts/{accountID}` requires an `ADMINISTRATOR` and an explicit full target state (`role`, `blocked`), so an omitted boolean cannot accidentally unblock someone. The API takes both its administration lock and the target voice-account lock before checking and changing state. It refuses an operation that would demote or block the last active administrator; a block revokes all target sessions and active logical voice leases with `BANNED`, and records actor ID, target ID and event type without private content. A role is looked up from the database on every authenticated request, so demotion takes effect without trusting an old client view or token claim.

`POST /api/v1/admin/categories` requires an `ADMINISTRATOR` and accepts a 1–80 Unicode-scalar name. The topology command takes its own transaction-level lock, appends a category at the next position, increments the one deployment topology revision and writes a metadata-only audit event. Reorder, rename, move and archive/delete semantics use the same revisioned topology model but remain separate commands.

`POST /api/v1/admin/categories/{categoryID}/channels` is the only current channel creation command and requires an `ADMINISTRATOR`. It accepts the same name constraint and a `TEXT` or `VOICE` kind, appends at the end of that category, increments topology revision and audits metadata. The schema and all updates deliberately omit a kind-changing operation; history cannot be converted into a different kind of room.

`PUT /api/v1/admin/categories/order` requires the entire category ID order and the revision last read by the client. It uses a transaction lock plus the expected revision, defers the named position constraint only inside that transaction, and changes all positions as one command. A stale revision, unknown ID or incomplete list has no topology effect and returns `409 CONFLICT` instructing the client to refresh before retrying.

`PATCH /api/v1/admin/categories/{categoryID}` renames a category with an explicit expected topology revision. It shares the topology lock with creation and reorder, advances revision only after both the target category and expected revision match, and otherwise returns `409 CONFLICT` without partial writes.

`PATCH /api/v1/admin/channels/{channelID}/category` moves a channel to the end of a target category under the same topology lock and expected revision. It changes only category and position: no route or update path changes the original `TEXT`/`VOICE` kind. A missing source/target or stale revision returns `409 CONFLICT` and leaves the topology unchanged.

`PUT /api/v1/admin/categories/{categoryID}/channels/order` takes the full order of that category only. It uses the topology lock, expected revision and a transaction-local deferred unique position constraint. Missing, duplicate, foreign-category or stale IDs fail as `409 CONFLICT` with no position or revision change; the command does not update channel kind or category.

`DELETE /api/v1/admin/channels/{channelID}` accepts only a body with `confirm_archive: true` and an expected revision. It is deliberately limited to a current `TEXT` channel: the command sets `archived_at`, advances topology revision and audits metadata, with no physical deletion or implicit history cascade. A `VOICE` channel must use the separate admission-close and lease-revocation workflow; this endpoint cannot falsely claim it disconnected media.

`POST /api/v1/admin/voice-channels/{channelID}/close-admission` accepts an expected topology revision and only changes a current `VOICE` channel. In one transaction it closes future logical admission, revokes every currently active voice lease for that channel with `CHANNEL_CLOSED`, writes a durable SFU revocation row for each affected lease, advances the revision and writes metadata-only audit data. The response counts logical leases only; it does not claim an already-connected participant was terminated until private RoomService completion is observed. The LiveKit enforcement and old-token test remain POC-03 gates.

`GET /api/v1/channels` requires any current non-blocked session and returns the ordered deployment topology plus its revision. It includes empty categories and only non-archived channels; a closed `VOICE` channel stays visible as `admission_closed: true`, which lets the client explain that it cannot be joined without inventing or hiding server state. It contains neither message history nor archived data.

`POST /api/v1/channels/{channelID}/messages` requires a current session and accepts `client_message_id`, body and optional `reply_to_id`. The body is valid UTF-8 with at most 8,000 Unicode code points; it is stored as plain text, not executable HTML. The command writes only to a current `TEXT` channel, and its one SQL statement permits a reply only to a message in that same channel. The `(author_id, channel_id, client_message_id)` constraint returns the original result, including its server `created_at` and revision, on a safe retry without persisting a duplicate or logging the message body.

`GET /api/v1/channels/{channelID}/messages` requires a current session and returns newest-first cursor pages of at most 100 messages from a current `TEXT` channel. The cursor is the last returned message ID and is always applied inside the path channel; a foreign or unavailable cursor yields no older page rather than crossing a conversation boundary. A deleted message retains its ID, author and timestamp with `deleted: true`, but its former text is returned as an empty body so neither history nor a reply preview can leak it.

Each text history item contains an `attachments` array only for its current non-deleted message. Every item has an attachment ID, original name and measured byte size in message order; it has no URL, storage key, MIME type or bytes. The client must use the separate protected download route for the same channel and must not treat history metadata as authorization. A deleted message returns `attachments: []` even if its old database link has not yet reached physical collection.

`GET /api/v1/channels/{channelID}/search` requires a current session and searches only non-deleted text of one current `TEXT` channel. PostgreSQL uses a generated `simple` full-text vector and `websearch_to_tsquery`, so Russian and English terms are case-insensitive and quoted words form an exact phrase. Results are newest-first and cursor-paginated; the request cannot search an archived/voice channel, another channel, attachment content or a deleted body.

`GET /api/v1/channels/{channelID}/attachments/{attachmentID}` requires a current session and rechecks the caller, current `TEXT` channel, `ATTACHED` state and a live same-channel message link before every private file read. Every unavailable condition returns one `404`; the route cannot serve an unattached object, a deleted message's file, a wrong channel or a local storage path. It always uses a binary `Content-Disposition: attachment` response with `nosniff`, so SVG, HTML and other active formats are not rendered on the application origin.

`PATCH /api/v1/channels/{channelID}/messages/{messageID}` changes a current, non-deleted `TEXT` message only when the session principal is its author and the supplied `expected_revision` is current. The guarded SQL update increments `revision`; a missing, deleted, non-owned, stale or unavailable message is the same `409 CONFLICT` response, without revealing which condition applied.

`DELETE /api/v1/channels/{channelID}/messages/{messageID}` soft-deletes the current message when the session principal is its author, or when its verified current role is `ADMINISTRATOR`. The atomic command replaces the stored body with the deleted marker, advances `revision`, retains IDs/timestamps for replies and history, and writes metadata-only audit data. Missing, deleted, unavailable and unauthorised targets share `404 NOT_FOUND`.

`GET /api/v1/direct-messages` returns only canonical pairs containing the authenticated caller. Each item includes a caller-local `unread_count`: messages authored by the other participant whose `(created_at, id)` is after that caller's persisted cursor. It does not return a message body, unseen-message timestamp, other participant's cursor, role or block state. A missing caller cursor counts all other-author messages; retained history and this count remain available after a block. The count becomes user-visible only when the frontend implements its navigation state.

`GET /api/v1/direct-message-candidates` returns a cursor-paginated page of other non-blocked accounts in this one deployment for the sole purpose of starting a DM. It excludes the caller and returns only the candidate ID and display name, never login, role or block state. A listed account can still become unavailable before selection, so the canonical `POST /api/v1/direct-messages` transaction remains the final active-participant check and pair-creation authority.

`GET /api/v1/direct-messages/{directMessageID}/search` searches only non-deleted text in the caller's selected canonical DM pair. PostgreSQL uses a generated `simple` full-text vector and `websearch_to_tsquery`, so Russian and English terms are case-insensitive and quoted words form an exact phrase; the query never selects another pair merely because the caller is an administrator. Results are newest-first, cursor-paginated and contain no attachment, deleted-message or other-DM data.

`PUT /api/v1/direct-messages/{directMessageID}/read-cursor` accepts a `message_id` only after the browser has shown that message in its active visible DM. The server derives the acting account from its current session, verifies in one SQL command that both the caller and selected message belong to the same canonical pair, and advances only that account's cursor by `(message_created_at, message_id)`. A delayed acknowledgement never moves the cursor backward: the `200` response returns the already newer effective cursor. Administrator role is not an exception, and the retained DM history may still be marked read after a block. The API cannot observe visibility itself; frontend code must not call this endpoint from a hidden tab or an unselected conversation. This command itself does not return a navigation count or desktop notification.

`POST /api/v1/voice/channels/{channelID}/leases` is available to every authenticated, non-blocked member. It serializes channel topology and the account's lease state, validates the current server-side session plus an active `VOICE` channel, and creates one logical lease tied to the digest of that session. If another lease is active, the response is `409 ACTIVE_VOICE_LEASE` and provides its channel ID; only an explicit `transfer: true` revokes the prior lease before issuing a new one. This response is deliberately not a media token and is not evidence of a completed LiveKit connection.

`DELETE /api/v1/voice/leases/{leaseID}` is an idempotent voluntary leave. It takes the same account lock and revokes a lease only when its user and issuing session digest match the current principal; a different tab cannot silently release an active connection it did not create. It does not assert that a connected LiveKit participant has already been forced out.

`POST /api/v1/admin/accounts/{accountID}/voice-kick` is administrator-only. It takes the target account's voice lock, revokes every current logical lease with `KICK`, writes a durable SFU revocation row for each affected lease, and writes metadata-only audit rows. The response counts logical leases only: real-time LiveKit disconnect, old-token rejection and blocked automatic reconnect remain POC-03 evidence requirements.

`POST /api/v1/voice/leases/{leaseID}/credential` performs a new database lookup before signing: lease ID, issuing session digest, owner, active `VOICE` channel, open admission and non-blocked account must all still match. Its token is restricted to `voice:{channelID}`, identity `voice-lease:{leaseID}`, `RoomJoin`, microphone/screen/audio-screen publication and subscription; it carries no room-admin grant and expires after one minute. It is returned only in the response and never logged. A current lookup and short expiry are defence-in-depth, not proof that an already-issued token is revocable; POC-03 remains required.

`GET /api/v1/auth/session` is the initial protected bootstrap route. Middleware recomputes the cookie digest and joins only a non-revoked session to a non-blocked user, so a stale cookie, logout or ban cannot recover old authority. It returns only current account ID and role; profile fields are delivered by the profile capability.

Authenticated commands must accept an idempotency key when retry could create state. Message creation uses `client_message_id` unique per author/conversation; a retry returns the original message instead of a duplicate. Edits use a message revision and return a conflict rather than overwriting a newer edit. Channel reorders use a topology revision and return HTTP 409 with refreshed state on conflict.

`GET /api/v1/realtime` upgrades only after the current server-side session middleware verifies the opaque cookie. The first current implementation sends a UUID `connection.ready` event. If a client supplies an `after` cursor, it explicitly emits `connection.resync_required` instead of claiming it can replay unimplemented or unverified history; the client refreshes its protected topology and active text history. Every 15 seconds the server verifies the same opaque cookie again and closes an invalidated connection with WebSocket policy-violation status, without sending a privileged "revoked" event or exposing the token. The connection uses the WebSocket library's default same-origin check, carries no token in its URL or payload, and it is independent from a healthy LiveKit/WebRTC connection.

Server events use the JSON Schema in `contracts/realtime.schema.json`; `event_id` supports replay/deduplication, `occurred_at` is server time, and `kind` selects a typed payload. Reconnect must not grant new authority: it may replay only authorized state after the last acknowledged event. Events, counters, previews, searches and attachment URLs apply the same conversation ACL as REST.

LiveKit credentials are minted through an authenticated API command only after the API creates or transfers a current voice lease. The reverse proxy exposes the client `/rtc` signaling path but not LiveKit's management API; it sends every signal connection through the private lease-admission guard and skips logging the URI carrying its token. The API worker alone holds a private RoomService credential for participant removal; media tracks do not transit the Go API. A WebSocket interruption must not force a healthy WebRTC session to close, but the server can revoke admission on authoritative moderation events.

The screen-share panel displays the chosen target separately from browser capture settings and available LiveKit sender stats. Missing fields remain unavailable rather than being copied from the target profile; these local observations are never sent to API logs and are not POC or capacity evidence. A screen source reported as ended is stopped through the SDK before the UI offers a new explicit picker action.

The remote screen viewer reads only LiveKit `remoteParticipants` of the room joined by the current room-scoped credential. It joins with screen tracks unsubscribed, keeps unselected screen audio/video unsubscribed, and attaches only the explicitly selected stream to one local video/audio pair. Remote microphone publications are separately enabled and attached to owned local audio elements so ordinary room voice does not depend on a screen selection. Deafen mutes every such remote microphone element and the selected screen-audio element, disables the local published microphone, and restores only the microphone state that existed before deafen; it does not stop local screen publication. The credential retains its lease identity but carries signed `account:<UUID>` metadata, which the client validates before using it as a local volume-preference key. Participant microphone and selected-stream audio levels are separate `0…200%` Web Audio gains; if Web Audio cannot be created the UI keeps a truthful capped HTML-media fallback. Preferences are local to the deployment origin and authenticated browser account, survive a reload, and intentionally do not synchronize to another browser/device. Participant cards include every remote participant in the room, an observable `RemoteTrackPublication.isMuted` label and a persisted local volume even before that participant's audio track attaches. `ActiveSpeakersChanged` is intersected with the room's remote participants and rendered as text plus a visual dot; it neither inspects audio samples nor represents microphone permission, network quality, moderation state, a server-side metric or another user's deafen state. This client discipline does not prove SFU enforcement, metadata visibility, acoustic amplification quality, speaker-event behavior, remote mute propagation, prevent a malicious modified client, or satisfy the browser/Windows/macOS media POC.

The browser supplies a bounded LiveKit reconnect policy (six exponential attempts with jitter) and renders `RECONNECTING` separately from mute, listener mode and voluntary exit. It does not invent a post-disconnect rejoin after the SDK gives up: the current logical lease is released and a user must explicitly join again. This keeps a client reconnect loop from bypassing future kick, ban, logout, channel deletion or revocation enforcement; actual browser and SFU behaviour remain POC-03 evidence work.
