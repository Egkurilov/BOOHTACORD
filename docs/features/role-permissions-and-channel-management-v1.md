## 1. Цель и согласованный объём

### 1.1. Цель

Обычный участник самостоятельно создаёт место для общения. Если администратор разрешил удаление соответствующего типа, участник может убрать любой такой объект. Для этого не нужен вход в админку, знание скрытого жеста или обращение к администратору.

### 1.2. Обязательные решения

| ID | Требование |
|---|---|
| R-01 | Две роли: `ADMINISTRATOR` — «Администратор», `MEMBER` — «Пользователь». Новые роли не создаются |
| R-02 | У MEMBER шесть независимых разрешений: создание/удаление TEXT, VOICE и раздела |
| R-03 | Исходная политика MEMBER: все три create = true, все три delete = false |
| R-04 | Настройки относятся ко всем текущим и будущим участникам MEMBER, а не к выбранному человеку |
| R-05 | Создание/удаление разрешены во всех доступных общих разделах. Нет category-level overrides |
| R-06 | Разрешённое удаление распространяется на любые объекты соответствующего типа, включая чужие и созданные администратором |
| R-07 | У создателя нет специальных прав владельца; автор создания нужен только для аудита |
| R-08 | Переименование, перемещение, изменение порядка, роли, модерация и permission-настройки остаются административными |
| R-09 | Права ADMINISTRATOR не редактируются в этой форме; существующие системные ограничения и ACL сохраняются |
| R-10 | Гибридный UX: «+» в шапке списка, «+» у раздела, правый клик по месту и эквивалентная кнопка «⋯» |
| R-11 | TEXT удаляется логически через архивирование; VOICE — через закрытие входа и подтверждённое завершение; непустой раздел не удаляется |
| R-12 | Сервер проверяет актуальное разрешение при каждой операции. Скрытая кнопка не является защитой |
| R-13 | Изменения прав вступают в силу на сервере после commit без повторного входа; клиенты обновляют интерфейс |
| R-14 | Открытие меню и создание объекта не переключают текущую беседу и не подключают пользователя к голосу |
| R-15 | Все способы вызова используют один набор действий и один сценарий выполнения, без раздельной бизнес-логики |

### 1.3. Что не входит

Не вводятся владельцы, пользовательские исключения, приватные каналы, пароли комнат, приглашения, временные комнаты, заявки на одобрение, вложенные разделы, клонирование, массовое удаление, управление участниками канала, самостоятельная перестановка каналов участниками. Нет квот «два своих канала» и персональных списков владельцев. Интерфейс просмотра/восстановления архива — отдельная задача. Не требуется предварительная реорганизация монорепозитория или замена state-management framework.

Система не превращается в универсальный редактор RBAC: в v1 управляются только шесть перечисленных действий. Термин «разрешения» используется в UI, техническое `permission` — в контрактах.

## 2. Модель разрешений

### 2.1. Канонические ключи

| Ключ | Название в админке | MEMBER, исходно | ADMINISTRATOR |
|---|---|:---:|:---:|
| `channel.text.create` | Создавать текстовые каналы | true | true |
| `channel.text.delete` | Удалять текстовые каналы | false | true |
| `channel.voice.create` | Создавать голосовые каналы | true | true |
| `channel.voice.delete` | Удалять голосовые каналы | false | true |
| `category.create` | Создавать разделы | true | true |
| `category.delete` | Удалять разделы | false | true |

В UI «раздел» соответствует существующей `category` в API/БД. Не вводить вторую сущность Section.

`create` не подразумевает `delete`, и наоборот. Разрешено сохранить любую из 64 комбинаций шести boolean, включая «всё выключено» и «только удаление». Нельзя автоматически включать создание при включении удаления.

### 2.2. Эффективное разрешение

Последовательность решения на сервере:

1. Сессия существует, действительна, принадлежит текущему активному и незаблокированному аккаунту.
2. Определены текущая роль и реальный объект операции; роль из клиентского запроса не принимается.
3. Для ADMINISTRATOR шесть действий разрешены; для MEMBER прочитано значение из сохранённой политики.
4. Проверены бизнес-условия: существование/состояние объекта, тип, пустота раздела, подтверждение удаления, revision и ограничения частоты.
5. Выполнена атомарная команда.

ADMINISTRATOR не обходит блокировку аккаунта, проверку сессии, пустоту раздела, TEXT/VOICE state machine или приватность DM. Разрешение `channel.voice.delete` не выдаёт общий `kick`, LiveKit admin credential или доступ к управлению аккаунтами.

Если политика отсутствует/невалидна из-за ошибки миграции, для MEMBER нет fallback «разрешить create». Возвращается ошибка доступности политики; остальные функции общения по возможности продолжают работать. Defaults — явное начальное состояние в БД, а не разрешающий fallback. Проверка на каждом запросе и deny-by-default для неизвестных действий соответствуют `[E1]`; конкретные исходные create-grants — согласованное продуктовое решение.

### 2.3. Важные комбинации

| Состояние MEMBER | Что доступно |
|---|---|
| Все create=true, delete=false | Создание разделов/TEXT/VOICE, никаких удалений |
| Только `channel.voice.create` | Голосовой канал в существующем разделе; создание раздела недоступно |
| Только `category.create` | Только новый пустой раздел |
| Только `channel.text.delete` | Удаление любого активного TEXT; создание, VOICE и разделы недоступны |
| Только `category.delete` | Удаление пустого раздела; убрать его содержимое самостоятельно нельзя |
| Все false | Обычное общение без мутаций топологии |
| Все true | Все шесть операций; по-прежнему без переименования/перемещения/модерации |

## 3. Админка «Роли и разрешения»

### 3.1. Путь и компоновка

**Администрирование → Роли и разрешения.** Вход доступен только текущему ADMINISTRATOR. Прямой переход MEMBER на экран не делает защищённых запросов редактирования и показывает отказ; backend независимо запрещает доступ.

На широком экране слева две роли, справа выбранная политика. На узком — переключатель двух ролей и карточки разрешений. При первом открытии выбрана «Пользователь»: это единственная редактируемая роль. Существующий экран назначения роли конкретному аккаунту остаётся отдельно и не дублируется здесь.

```text
Администрирование / Роли и разрешения

Роли                      Пользователь
  Администратор           Эти настройки действуют для всех участников
> Пользователь            с ролью «Пользователь».

                          Объект                 Создавать    Удалять
                          Текстовые каналы          [✓]          [ ]
                          Голосовые каналы          [✓]          [ ]
                          Разделы                   [✓]          [ ]

                          Удаление разрешает воздействовать на чужие
                          каналы и каналы, созданные администраторами.
                          Непустые разделы удалять нельзя.

                          [По умолчанию]   [Отменить изменения] [Сохранить]
```

Это текстовый wireframe, не новый визуальный стиль. Использовать текущие tokens, типографику, spacing и компоненты админки. Название/код роли не редактируются. Нет кнопок добавления и удаления ролей.

### 3.2. Экран ADMINISTRATOR

Шесть значений отображаются включёнными и только для чтения. Сообщение: **«Администраторы управляют каналами и разрешениями. Изменить эту роль здесь нельзя».** Кнопок «Сохранить» и «По умолчанию» нет. Другие административные возможности не представляются как редактируемые false/true в этой сетке.

### 3.3. Сохранение и предупреждение

Галочки изменяют только локальный черновик. Автосохранения нет. «Сохранить» доступно при отличии от серверного снимка и валидном состоянии загрузки.

Если среди изменений есть хотя бы одно `delete: false → true`, нажатие «Сохранить» открывает подтверждение:

> **Разрешить пользователям удаление?**  
> Все участники роли «Пользователь» смогут удалять: **[перечень вновь разрешённых объектов]**. Это касается чужих каналов и каналов администраторов. Текстовые каналы будут архивироваться; закрытие голосового отключит его участников; удалить можно только пустой раздел.
>
> **Отмена** · **Разрешить и сохранить**

В списке только действительно вновь включаемые виды. Начальный фокус — «Отмена». Существующее true→true не вызывает повторного подтверждения при несвязанной правке. На время запроса редактирование блокируется, показывается «Сохраняем…».

При успехе серверный ответ становится новым baseline, dirty=false, появляется устойчивый inline-статус: **«Разрешения сохранены. Они применены ко всем пользователям этой роли».** Статус не является обещанием мгновенной доставки UI-события каждому офлайн-устройству. Открытые активные клиенты обновляются по разделу 11.

### 3.4. Сброс и уход со страницы

«По умолчанию» устанавливает create=true/delete=false **только в локальном черновике**. Для применения нужен «Сохранить». «Отменить изменения» возвращает последний загруженный серверный снимок, а не заводские defaults.

При уходе, смене роли в редакторе или закрытии панели с dirty=true: **«Есть несохранённые изменения» → «Остаться» / «Не сохранять и выйти»**. Если активный ADMINISTRATOR был понижен, возможность редактирования прекращается: несохранённые настройки никогда не отправляются от имени нового аккаунта.

### 3.5. Конкурентное редактирование

Редактор получает `revision`. PUT передаёт `expected_revision`. Два администратора не могут молча перезаписать друг друга.

При 409: сохранить локальный черновик; показать **«Разрешения уже изменены другим администратором. Загрузите актуальные настройки и проверьте отличия»**. Доступны «Загрузить актуальные» и «Отменить мои изменения». После загрузки показать для изменённых строк: серверное значение / мой вариант. Повтор разрешён после явной проверки нового baseline; для повторно включаемого удаления снова требуется подтверждение. Автоматического merge и blind overwrite нет.

Если сетевой ответ потерян, выполнить GET. Совпадение шести значений с отправленными означает только **«На сервере уже действуют выбранные настройки»**, а не доказательство, кто их записал. Отличие показывает текущий серверный снимок и сохраняет локальный draft для решения администратора. Повтор PUT с прежней revision не создаёт вторую запись аудита изменения.

### 3.6. Загрузка и ошибки

| Состояние | UI |
|---|---|
| Начальная загрузка | Skeleton/индикатор, controls недоступны; не рисовать defaults как сохранённые |
| GET не удался | «Не удалось загрузить разрешения» + «Повторить», без возможности сохранить неизвестный baseline |
| PUT 400 | Ошибка конкретного поля/подтверждения, draft сохранён |
| PUT 403 | «У вас больше нет прав администратора», редактор закрывается/становится недоступным |
| PUT 409 | Сценарий сравнения ревизий, без потери draft |
| PUT 5xx/timeout | Не показывать успех; сверка с сервером/повтор |
| Нет изменений | «Сохранить» выключено |

## 4. Пользовательская навигация — выбранный гибридный вариант

### 4.1. Точки входа

| Точка | Действие | Видимость |
|---|---|---|
| Постоянный «+» в шапке «Каналы» | Меню глобального создания | Если разрешено создание хотя бы одного типа объекта |
| «+» справа у раздела | Сразу форма создания канала с выбранным разделом | Если разрешён TEXT.create или VOICE.create |
| «⋯» у раздела/канала | Меню объекта | Если есть хотя бы одно отображаемое действие |
| Правый клик по пустому месту списка | То же меню, что глобальный «+» | Только в области навигации; не единственный вход |
| Правый клик по разделу/каналу | То же меню, что соответствующее «⋯» | Содержимое определяется местом клика |
| Долгое нажатие на touch | Дополнительный вход в то же меню объекта | Не заменяет видимый «⋯» |

Шапка остаётся доступной при прокрутке списка. «+» у раздела видим постоянно, но визуально вторичен. У канала нет «+»: канал не содержит дочерних каналов. На desktop «⋯» может появляться при hover/focus-within; клавиатурная кнопка не исчезает при получении фокуса. На touch «⋯» всегда виден при наличии действий.

**Контекст определяется стабильными ID, не текущим выбранным каналом и не индексом строки.** Правый клик не вызывает select/join, «+» не сворачивает раздел. Контекстные menus открываются у курсора или кнопки с ограничением границ viewport; одновременно открыто одно меню.

### 4.2. Точный состав меню MEMBER

| Контекст | Пункты в порядке отображения |
|---|---|
| Шапка / пустое место | «Создать канал…»; «Создать раздел…» |
| Раздел | «Создать канал…»; разделитель; «Удалить раздел…» |
| TEXT | «Создать канал в “{раздел}”…»; разделитель; «Удалить текстовый канал…» |
| VOICE | «Создать канал в “{раздел}”…»; разделитель; «Удалить голосовой канал…» |

«Создать канал…» требует хотя бы одного channel.create. «Создать раздел…» требует category.create. Каждый delete требует собственного permission. Ненужные разделители удаляются. Отсутствующее разрешение скрывает пункт; если ни одного пункта нет, скрывается «⋯» и собственное меню не открывается. Нельзя показывать пустую рамку или перехватывать контекстное меню браузера без замены.

Если право есть, но действие временно невозможно, пункт остаётся с `disabled` и объяснением. Примеры: непустой раздел; VOICE уже закрывается; состояние нужного объекта ещё загружается. Disabled-пункт не выполняет команду ни мышью, ни клавиатурой. Причина доступна не только hover-tooltip, но и screen reader/touch-представлению.

Администратор получает эти же новые входы, а его существующие rename/move/reorder остаются доступны через общую административную реализацию. Их нельзя случайно показать MEMBER с шестью включёнными разрешениями. Создание/удаление не дублируются в одном меню дважды.

### 4.3. Границы обработки событий

Обрабатывать `contextmenu` только внутри списка каналов: строка категории, строка канала и явно отмеченная свободная область. Не перехватывать событие на input/textarea/contenteditable, тексте переписки, медиа, внешних ссылках, voice dock и списке участников. Пустота внутри кнопки строки не считается глобальным пустым пространством: цель определяется ближайшим контекстным контейнером.

Для открытия справа использовать `contextmenu`, а не любой `pointerdown`. Кнопки вызывают `stopPropagation` там, где родитель выбирает/сворачивает объект. Enter/Space на «⋯» открывает меню и не запускает действие строки. Touch long-press отменяется при начале прокрутки и не порождает последующий click/join.

При удалении/перемещении контекстного объекта открытое меню закрывается. Если категория переименована, контекст остаётся тем же ID; видимые названия обновляются. При любом действии повторно проверяется существование объекта в актуальной topology и разрешение; меню не хранит самостоятельную копию прав.

## 5. Создание канала и раздела

### 5.1. Одна форма канала для всех входов

**Заголовок:** «Создать канал». Поля:

| Поле | Спецификация |
|---|---|
| Тип | Radio/segmented TEXT «Текстовый» и VOICE «Голосовой». Показывать только разрешённые типы. При двух исходно TEXT; при одном выбрать его без лишнего выбора |
| Название | Обязательное; правила 5.2; фокус при открытии |
| Раздел | Обязательный select по ID; все текущие разделы, в серверном порядке |
| Подсказка | «Канал будет доступен всем участникам. Управление зависит от прав вашей роли» |
| Кнопки | «Отмена», «Создать канал» |

При входе от раздела/соседнего канала категория предвыбрана. Пользователь может изменить её на другую существующую; это создание, не разрешение на перемещение существующего канала. При глобальном входе: если раздел один — выбран он; если несколько — placeholder «Выберите раздел», без неявной привязки к активному каналу.

Нет промежуточного меню «Текстовый/Голосовой» перед этой формой. Тип выбирается внутри. Не наследовать тип соседнего канала и не копировать его название/права.

### 5.2. Название

Повторно использовать серверный валидатор названий проекта, включая подсчёт 1–80 Unicode code points `[S2]`. В v1 зафиксировать trim внешних пробельных символов и запрет имени, пустого после trim. Регистр, внутренние пробелы, кириллица и emoji сохраняются; имя не превращается автоматически в slug и к нему не добавляется `#` как часть данных. Иконка `#` — только presentation.

Новые name validators не должны вводить свою несовместимую трактовку длины. Если текущий валидатор не обрабатывает перевод строки/управляющие символы, добавить единое правило запрета для всех интерфейсов именования и обновить контракт, а не только web. Проверки с surrogate pair/emoji обязательны. В HTML имя выводится как текст, не `v-html`.

Текущее ограничение уникальности имён документами не подтверждено. **Целевое решение v1:** разрешить совпадающие названия; идентичность — UUID. Не использовать имя для дедупликации запроса. При совпадении в том же разделе можно показывать мягкое предупреждение, но оно не требуется для релиза. Если в реальной БД есть уникальный индекс по имени, это явно отражается в preflight; нельзя удалить индекс молча или начать противоречить API. При наличии такого индекса адаптировать его в отдельной рассмотренной миграции под целевое правило.

### 5.3. Отсутствие разделов

Если разделов нет и category.create разрешён, экран предлагает «Сначала создайте раздел» и кнопку «Создать раздел». Переход выполняется последовательным шагом, а не двумя наложенными диалогами. Черновик типа/имени канала сохраняется; после создания раздел подставляется и пользователь отдельно подтверждает создание канала.

Если category.create запрещён, объяснение: **«Для создания канала нужен раздел. Попросите администратора создать его».** Channel.create при этом не изменяется. Нет автоматического системного раздела, скрытой выдачи category.create или канала без категории.

Если раздел удалили во время ввода, сохранённое название/тип не теряются, поле раздела становится невалидным: «Этот раздел удалён. Выберите другой». Не переносить канал молча в первый доступный раздел.

### 5.4. Отправка и успех

Нажатие «Создать канал» фиксирует payload и `client_request_id`. На время запроса кнопка disabled с «Создаём…»; повторный click/Enter не запускает второй запрос. Успешный server response означает созданный объект, но не вход в него.

Клиент загружает актуальную topology. Канал находится в конце выбранного раздела; раздел раскрывается. Для локального создателя строка кратко подсвечивается (предлагается 3 секунды, без анимации при reduced motion). Список допускает локальную прокрутку до нового объекта; центральная беседа, её draft и активное media не переключаются.

Устойчивый inline-статус над списком:

- TEXT: **«Текстовый канал “{name}” создан» · «Открыть»**.
- VOICE: **«Голосовой канал “{name}” создан» · «Подключиться»**.

Действия вызывают существующие сценарии навигации/join, включая предупреждения и transfer при необходимости. Остальные пользователи просто получают новую строку без принудительного раскрытия, прокрутки или изменения выбора. Успешный HTTP с неудачным refresh показывает **«Канал создан, но список пока не обновился» · «Обновить список»**, а не предлагает создать заново.

### 5.5. Создание раздела

Вход: глобальный «+» или меню пустого пространства → «Создать раздел…». Форма содержит только название и «Отмена / Создать раздел». Название проверяется по тем же правилам. Новый раздел добавляется в конец, раскрывается, показывает «Пока нет каналов» и доступное действие «Создать канал» при наличии channel.create.

Создание раздела не запускает автоматически создание канала, кроме явно начатого двухшагового сценария 5.3. Если второй шаг отменён, раздел остаётся: это две независимые успешные операции, не неявная транзакция с откатом.

## 6. Удаление: подтверждения и завершение

### 6.1. Общие правила

Удаление вызывается только из меню конкретного объекта. В глобальном меню его нет. Перед запросом показываются название, тип и последствия; пользователь подтверждает действие явно. Начальный фокус не на опасной кнопке. Проверка права повторяется при открытии и отправке, серверный отказ остаётся окончательным.

После отзыва delete открытый диалог не отправляет операцию. Сообщение: **«Ваши права изменились. Удаление больше недоступно»**. Закрытие диалога не восстанавливает право. Если запрос уже мог уйти, его результат сначала сверяется: отзыв права не означает, что ранее начатая операция была отменена.

### 6.2. TEXT

**Заголовок:** «Удалить текстовый канал “{name}”?»  
**Текст:** «Канал исчезнет из списка у всех участников. История сохранится, но читать и продолжать переписку через этот канал будет нельзя. Восстановление через этот экран недоступно».  
**Кнопки:** «Отмена» / «Удалить канал».

Используется существующая семантика archive, не SQL cascade. `archived_at` закрывает обычные историю/поиск/вложения через прежние ACL. Не обещать пользователю готовый браузер архива. Ранее опубликованные сообщения и их данные не физически удаляются этой командой `[S2]`.

После подтверждённого успеха канал исчезает из списка. Если открыт другой канал/DM — он не меняется. Если открыт удаляемый TEXT, центральная область становится **«Канал удалён»** с предложением выбрать другой, без случайного перехода.

**Защита локального ввода.** До очистки выбранного TEXT сохранить его несохранённый текст/inline-edit в account-scoped памяти и показать «Скопировать неотправленный текст» / «Закрыть». Это узкий сценарий удаления, не глобальное автосохранение переписок. Буфер очищается по явному закрытию, logout или смене аккаунта; не отправляется на сервер и не пишется в localStorage. Уже отправленный, но ещё не подтверждённый payload не переносится в другой канал. In-flight upload перестаёт быть доступным для новой привязки; отмена и поздний ответ обрабатываются прежними account/conversation guards. Опубликованное не превращается в новое сообщение автоматически.

Этот сценарий нужен и у автора удаления, и у других участников, если канал архивирован при их открытом composer. HTTP-ошибка сети сама по себе не считается доказательством удаления: нужен авторитетный topology/ACL-ответ. `[S1]`, FE-18 сейчас очищает drafts при смене беседы; здесь требуется отдельная доработка перед unmount.

### 6.3. VOICE

**Заголовок:** «Удалить голосовой канал “{name}”?»  
**Текст:** «Вход в канал будет закрыт. Подключённые участники будут отключены, трансляции завершатся».  
**Кнопки:** «Отмена» / «Удалить канал».

Если есть свежий roster, можно добавить число участников. Если roster неизвестен/устарел, не показывать «0»: общий текст о возможных участниках остаётся. Это число информационное и не решает вопрос удаления. При выданном voice.delete пользователь может удалить занятую комнату — ограничение «только пустую» не вводится.

Цепочка:

```text
OPEN
  → закрыть admission + отозвать leases + поставить SFU-removal в очередь
CLOSING (виден, новые подключения запрещены)
  → все удаления подтверждены + active leases отсутствуют + LiveKit подтвердил пустоту
ARCHIVED (исчезает из активной topology)
```

Первый успешный ответ означает **«Закрытие начато»**, а не «Все уже отключены». Строка остаётся с «Закрывается…», join и повторное удаление недоступны. Ошибка LiveKit оставляет CLOSING с объяснением/диагностикой для администратора; по таймеру успех не придумывается. Финализация выполняется существующим worker, независимо от закрытого браузера и текущих прав инициатора `[S1]`, BE-06, FE-14.

Выход из собственной голосовой сессии остаётся доступен даже при CLOSING или исчезновении комнаты. Повторный вход со старым credential должен быть запрещён существующим admission guard. Участники получают адресное `voice.lease_revoked` только своего lease; остальные комнаты не затрагиваются. Если инициатор не состоит в этой комнате, его активное media в другом канале не прерывается.

### 6.4. Раздел

**Пустой раздел** — нет ни одного неархивированного канала, включая VOICE в CLOSING. Лишь визуально свёрнутый раздел не считается пустым.

Непустой: пункт «Удалить раздел…» disabled, текст **«Сначала уберите каналы из раздела. Перенос доступен администратору»**. Отсутствие channel.delete не выдаёт его автоматически. Никакой кнопки «Удалить всё вместе».

Пустой: подтверждение **«Удалить раздел “{name}”? Раздел исчезнет у всех участников»**. После commit исчезает из списка, соседние разделы/выбор канала не меняются.

**Архивная история и внешние ключи.** Архивированные каналы могут сохранять category_id. Поэтому целевая операция логически удаляет раздел из актуальной topology, сохраняя техническую запись для исторических связей. Если текущий delete-empty уже гарантирует это, переиспользовать его. Иначе добавить tombstone `categories.deleted_at` и фильтрацию; не заменять FK на `ON DELETE CASCADE`, не физически удалять архивные сообщения ради удаления пустого UI-раздела. Это новое проектное уточнение, не утверждение о текущей схеме БД.

Если между открытием подтверждения и commit другой участник создал канал, удаление возвращает конфликт и ничего не удаляет. После refresh раздел остаётся, причина отображается пользователю.

## 7. Пользовательские состояния и ошибки

### 7.1. Общая state machine формы

```text
CLOSED → EDITING → SUBMITTING → SUCCEEDED → CLOSED
                ↘ VALIDATION_ERROR → EDITING
SUBMITTING → REJECTED → EDITING / ACCESS_LOST
SUBMITTING → RESULT_UNKNOWN → RECONCILING → SUCCEEDED / SAME_REQUEST_RETRY
```

Timeout после отправки — `RESULT_UNKNOWN`, не «ничего не создано». Нельзя заменить ключ и отправить ещё раз. На время неизвестного результата payload заморожен; «Проверить результат» и безопасный retry используют прежний ID. После доказанного отказа без записи можно менять payload и выдавать новый ID при следующей отправке. Полная политика идемпотентности — раздел 12.

Escape/крестик закрывает форму, но **не отменяет уже принятый сервером запрос**. Во время SUBMITTING/RESULT_UNKNOWN состояние операции продолжает жить в account-scoped controller; inline-статус над списком показывает результат. Не разрешать бессрочно запирать пользователя в модальном окне. Повторное открытие того же незавершённого действия предлагает его проверить, а не создаёт новую команду.

### 7.2. Тексты и поведение

| Ситуация | Текст | Действие |
|---|---|---|
| Имя пусто | «Введите название» | Фокус/ошибка у поля |
| Более 80 code points | «Название не должно превышать 80 символов» | Не обрезать молча |
| Раздел не выбран | «Выберите раздел» | Открыть/подсветить select |
| Раздел исчез | «Этот раздел удалён. Выберите другой» | Сохранить имя/тип |
| Право отозвано | «Ваши права изменились. Это действие больше недоступно» | Refresh permissions; disable submit |
| Сессия завершена | Стандартный путь повторного входа | Очистить account-bound данные; не переносить draft следующему пользователю |
| 429 | «Слишком много действий. Повторите через {n} секунд» | Уважать Retry-After; не автоспамить |
| Результат неизвестен | «Ответ сервера не получен. Проверяем результат…» | Сверка/повтор с тем же ID |
| Топология изменилась | «Список каналов изменился. Обновите данные и подтвердите действие ещё раз» | Refresh; прежний выбор по ID |
| Объект уже удалён | «Канал уже удалён. Список обновлён» / аналог для раздела | Не показывать новый успех от своего имени |
| VOICE не финализирован | «Канал закрывается. Ожидаем отключения участников» | Без нового удаления и false success |
| Политика не загрузилась | «Не удалось проверить разрешения» | Retry, мутации недоступны; общение не выключается |

Изменение политики не отменяет ранее созданные объекты, не архивирует каналы, не сбрасывает чтение и не отключает voice. Право на создание/удаление не является правом на чтение/участие.

## 8. Платформы, доступность и визуальное поведение

### 8.1. Одинаковая модель, подходящая оболочка

| Клиент | Меню объекта | Форма | Админка |
|---|---|---|---|
| Web desktop / Windows / macOS | ПКМ или «⋯», anchored menu | Диалог | Две роли + сетка шести значений |
| Web touch / iOS / Android | «⋯»; long-press как дубль | На узком экране отдельная полноэкранная форма | Переключатель ролей + три карточки Create/Delete |
| Платформа с клавиатурой и touch | Оба способа, один action resolver | По доступной ширине | Те же разрешения и сохранение |

Нижнее меню на телефоне не содержит уникальных возможностей. Back/Escape закрывает сначала вложенное меню, затем форму; не выходит из голоса. Прокрутка, safe area и клавиатура не перекрывают «Создать»/«Сохранить». Предлагаемая touch-зона кнопок — не меньше 44×44 логических единиц; это целевой UI-параметр, не заявление о сертификате доступности.

### 8.2. Keyboard и assistive technologies

Меню: Enter/Space открывает с фокусом на первом пункте; стрелки перемещают, Home/End — начало/конец, Enter выполняет; Escape закрывает и возвращает фокус. Tab выводит фокус из меню, не циклирует пункты. Shift+F10/Context Menu открывает меню сфокусированного объекта там, где платформа поддерживает. Disabled-пункт с объяснением доступен для прочтения, но не активируется. Для web использовать button, `aria-haspopup`, `aria-expanded`, `role=menu/menuitem`, `aria-disabled` по `[E2–E3]`.

Диалог удерживает Tab внутри, фон inert, есть видимая кнопка закрытия. Создание фокусирует название; подтверждение опасного действия — безопасную кнопку. После закрытия фокус возвращается триггеру; если объект удалён, ближайшему подходящему разделу/шапке списка. Заголовок и связанные ошибки доступны screen reader. Это применение паттерна `[E4]`, а не проверка готового UI.

Галочки в админке имеют полное имя, например **«Пользователь: удалять голосовые каналы»**, а не просто «Удалять». Статусы не кодируются одним цветом; пояснения и ошибки озвучиваются через соответствующий status/alert. Действия доступны при 200% zoom и ширине 320 CSS px без потери controls. Проверить VoiceOver и NVDA/TalkBack на соответствующих клиентах.

Открытие меню/диалога не пересоздаёт LiveKit connection. Обработка клавиш в полях ввода не запускает PTT-команды; существующая защита от застрявшего PTT при потере фокуса сохраняется. История/выбранный канал не размонтируются только потому, что появилась модальная форма.

## 9. Backend: границы и сервисы

### 9.1. Место в системе

Сохраняется Go-монолит. Предлагаемые границы, не обязательное переименование существующих пакетов:

```text
internal/authorization/
  permission.go              # шесть констант и registry
  effective_permissions.go   # активная сессия + текущая роль + политика
  role_policy/               # чтение/сохранение с revision
  api/                       # DTO/HTTP новых endpoints
  postgres/                  # policy и атомарное сохранение

internal/channel/            # существующие create/archive/close/delete leaves
  ...                        # расширяются проверками, не копируются

internal/topology_command/   # либо существующая общая идемпотентность
  receipt.go
  postgres/
```

Backend policy evaluator не зависит от Vue/Flutter. Все mutation paths, включая старые admin adapters и будущие CLI, должны обращаться к тем же доменным проверкам. Нельзя заменить `requireAdministrator` на `requireAuthenticated` для всего router group: это откроет лишние операции.

### 9.2. Новые и прежние маршруты

Новые участнические операции получают нейтральные пути. Прежние `/api/v1/admin/*` сохраняют административный middleware, контракт и поведение для старых клиентов. Они становятся adapters к общей реализации; не отдельной моделью каналов.

| Новая операция | Метод и путь | Разрешение |
|---|---|---|
| Собственные эффективные права | `GET /api/v1/auth/permissions` | Любая действительная активная сессия |
| Роли и политики для редактора | `GET /api/v1/admin/roles` | Только ADMINISTRATOR |
| Изменение MEMBER | `PUT /api/v1/admin/roles/MEMBER/permissions` | Только ADMINISTRATOR |
| Создание раздела | `POST /api/v1/categories` | `category.create` |
| Создание канала | `POST /api/v1/categories/{categoryID}/channels` | `channel.text.create` или `channel.voice.create` по kind |
| Архивирование TEXT | `DELETE /api/v1/channels/{channelID}` | `channel.text.delete`; только реальный TEXT |
| Закрытие VOICE | `POST /api/v1/voice-channels/{channelID}/close-admission` | `channel.voice.delete`; только реальный VOICE |
| Удаление пустого раздела | `DELETE /api/v1/categories/{categoryID}` | `category.delete` |
| Результат собственной topology-команды | `GET /api/v1/topology-commands/{clientRequestID}` | Активная сессия и совпадение actor_id квитанции |

`GET /api/v1/channels` остаётся существующим авторизованным чтением topology. GET auth/session не ломается добавлением обязательных новых полей: permission snapshot получаем отдельным запросом. Нельзя выдавать разрешения гостью через публичный конфиг.

Все mutations сохраняют существующие cookie/Origin/CSRF-требования `[S2]`, строки 3–5; native передаёт необходимые заголовки по текущему контракту проекта. Клиентский `actor_id`, `role`, `owner_id` или `permissions` в topology body запрещён. Реальный тип канала берётся из БД, не из присланного поля `kind` на удалении.

### 9.3. Известные старые пути, которые не открываем MEMBER

Согласно `[S2]`: `POST /admin/categories`, `POST /admin/categories/{id}/channels`, `DELETE /admin/channels/{id}`, `POST /admin/voice-channels/{id}/close-admission`, rename/move/order endpoints. MEMBER вызывает только новые разрешённые маршруты. Старые web/native администраторы продолжают работать. Точное старое имя delete-empty категории проверить в checkout: данный API-документ его явно не перечисляет, поэтому оно здесь не выдумано.

Новые версии общей админской формы создания/удаления должны по возможности использовать тот же controller и нейтральные маршруты с idempotency, что и пользовательская навигация. Остальные административные действия не мигрируют автоматически.

## 10. Данные, контракты и HTTP

### 10.1. Сохраняемая политика

Рекомендуется одна таблица `role_permissions` со строкой `role = 'MEMBER'`, а не полноценный конструктор ролей:

| Поле | Смысл |
|---|---|
| `role` | PK, в v1 только MEMBER |
| `text_create`, `text_delete` | Boolean NOT NULL |
| `voice_create`, `voice_delete` | Boolean NOT NULL |
| `category_create`, `category_delete` | Boolean NOT NULL |
| `revision` | Положительный монотонный номер конфигурации |
| `updated_at` | Серверное время |
| `updated_by` | Actor UUID; nullable для первичной миграции |

ADMINISTRATOR — неизменяемый policy preset в коде, не редактируемая DB-строка. Список ключей и mapping на колонки задан явно. Клиент не передаёт bitmask. Для расширения новым ключом требуется миграция/контракт; неизвестное разрешение не становится true.

Первая migration вставляет MEMBER с create=true/delete=false и revision=1. Повторный deploy не перезаписывает строку. Существующие и новые участники получают одну актуальную политику без массового обновления `users`. Назначение роли аккаунту остаётся существующей возможностью.

### 10.2. GET собственных прав

`200 OK`, `Cache-Control: no-store`. Пример целевого DTO:

```json
{
  "account_id": "8e1de568-1c98-4d14-89e5-d2366f5a0dc0",
  "role": "MEMBER",
  "permissions_revision": 12,
  "permissions": {
    "channel.text.create": true,
    "channel.text.delete": false,
    "channel.voice.create": true,
    "channel.voice.delete": false,
    "category.create": true,
    "category.delete": false
  }
}
```

`permissions_revision` — версия редактируемой конфигурации, **не** topology revision и **не** версия личного назначения роли. Для ADMINISTRATOR response содержит ту же актуальную revision конфигурации, но все шесть effective values=true. Поэтому смена MEMBER→ADMINISTRATOR может менять effective values при той же revision; клиент обязан учитывать account/role и порядок собственных запросов.

### 10.3. GET ролей

Целевой ответ `GET /api/v1/admin/roles`:

```json
{
  "revision": 12,
  "roles": [
    {
      "role": "ADMINISTRATOR",
      "display_name": "Администратор",
      "editable": false,
      "permissions": {
        "channel.text.create": true,
        "channel.text.delete": true,
        "channel.voice.create": true,
        "channel.voice.delete": true,
        "category.create": true,
        "category.delete": true
      }
    },
    {
      "role": "MEMBER",
      "display_name": "Пользователь",
      "editable": true,
      "permissions": {
        "channel.text.create": true,
        "channel.text.delete": false,
        "channel.voice.create": true,
        "channel.voice.delete": false,
        "category.create": true,
        "category.delete": false
      }
    }
  ]
}
```

Defaults для кнопки «По умолчанию» — фиксированная часть versioned registry из раздела 2, проверяемая общим contract fixture. Не получать defaults из текущих значений роли: администратор мог их изменить.

### 10.4. PUT политики MEMBER

Полный набор шести boolean; пропущенные поля не считаются false. Дополнительные неизвестные ключи, null, строки вместо boolean и отрицательная revision отклоняются.

```json
{
  "expected_revision": 12,
  "permissions": {
    "channel.text.create": true,
    "channel.text.delete": false,
    "channel.voice.create": true,
    "channel.voice.delete": true,
    "category.create": true,
    "category.delete": false
  },
  "confirm_delete_grants": true
}
```

`confirm_delete_grants` обязателен как true при наличии новых delete-grants, иначе может быть false/отсутствовать. Это явное подтверждение опасного изменения, а не механизм аутентификации. Сервер самостоятельно сравнивает old/new под lock. При отсутствии подтверждения — `400 DELETE_GRANT_CONFIRMATION_REQUIRED`.

Успех: `200`, role, новая revision и полный сохранённый набор. Если payload равен текущему и expected_revision совпадает, вернуть текущее состояние без повышения revision/нового audit. Если revision устарела, всегда 409; не «проталкивать» совпадающие значения за чужой update. Запись политики, increment revision и audit — одна транзакция.

PUT для `ADMINISTRATOR` возвращает `403 ROLE_IMMUTABLE` для администратора; MEMBER до проверки целевой роли получает обычный отказ доступа. Другой role path — 404/стандартный unknown-role для администратора. UI не предлагает такие операции.

### 10.5. Создание

Новый раздел:

```json
{
  "client_request_id": "6bc49936-de95-4d9a-a4a8-e33a457b67c3",
  "name": "Игры"
}
```

Новый канал в path-категории:

```json
{
  "client_request_id": "9f954ba6-6cd0-42ca-a504-353ac45cb2e5",
  "kind": "VOICE",
  "name": "Вечерний iRacing"
}
```

Успех `201 Created`, унифицированный результат нового mutation API:

```json
{
  "client_request_id": "9f954ba6-6cd0-42ca-a504-353ac45cb2e5",
  "topology_revision": 43,
  "result": {
    "resource_type": "VOICE_CHANNEL",
    "resource_id": "20160d30-9eef-42f6-94ad-cf7a813119dd",
    "state": "ACTIVE"
  }
}
```

Результат описывает состояние **в момент commit**. Отображаемые имя, порядок, unread и другие текущие поля берутся из канонического GET topology. После HTTP успеха и до refresh не добавлять «оптимистический» канал с выдуманным ID.

При append-создании клиентская `expected_revision` не требуется: порядок и живой target проверяются под topology lock. Это соответствует подробному описанию create в `[S2]`, в отличие от reorder/delete. Сервер увеличивает общую revision. Два корректных создания не должны конфликтовать только потому, что оба начали с одной старой версии списка.

### 10.6. Удаление и voice-close

Для TEXT DELETE:

```json
{
  "client_request_id": "a04d7a53-63d6-4528-9af5-6c7c21737e3f",
  "expected_revision": 43,
  "confirm_archive": true
}
```

Для VOICE close-admission:

```json
{
  "client_request_id": "36b9e15c-280a-4f76-b8bf-b12d91af8da0",
  "expected_revision": 43,
  "confirm_close": true
}
```

Для category DELETE:

```json
{
  "client_request_id": "d38c4397-b019-45b4-a7b8-cecb7c8b7573",
  "expected_revision": 43,
  "confirm_delete": true
}
```

TEXT/category возвращают `200` с mutation result `ARCHIVED`/`DELETED`; новый VOICE endpoint — `202` с `CLOSING`. Прежние admin endpoints сохраняют прежние коды/DTO через adapter, поэтому существующие клиенты не ломаются из-за нового 202.

`expected_revision` проверяется вместе с target state и permission. После конфликта требуется новый refresh и подтверждение пользователя. Новое ожидаемое число не является разрешением удалить другой объект: resource ID остаётся прежним. Повтор уже успешно принятой команды обрабатывает receipt до проверки старой topology revision, но после действительной аутентификации и проверки нынешнего write-permission; доступный read-receipt описан далее.

### 10.7. Ошибки новых endpoints

Сохраняется базовый envelope `[S2]`: `error.code`, русское `message`, серверный `request_id`. У новых endpoints допускается описанный в schema безопасный `error.details`, например текущая revision, missing permission или retry seconds; не raw SQL/payload.

| HTTP / code | Значение | Клиент |
|---|---|---|
| 400 `VALIDATION_FAILED` | Имя/kind/boolean/UUID/body невалидны | Ошибки полей |
| 400 `DELETE_GRANT_CONFIRMATION_REQUIRED` | Новое право удаления не подтверждено | Повторить confirmation |
| 401 `UNAUTHENTICATED` | Нет действительной сессии | Стандартный auth lifecycle |
| 403 `PERMISSION_DENIED` | Конкретное действие не разрешено | Refresh прав, disable действие |
| 403 `ROLE_IMMUTABLE` | Попытка изменить preset admin | Не давать retry на то же изменение |
| 404 `CATEGORY_UNAVAILABLE` / `CHANNEL_UNAVAILABLE` | Неизвестный/удалённый target | Refresh без изменения выбора на чужой объект |
| 404 `COMMAND_NOT_FOUND` | Собственная receipt ещё не найдена | После timeout не означает, что запрос точно не выполняется |
| 409 `PERMISSIONS_REVISION_CONFLICT` | Конкурентная правка роли | Сохранить draft, сравнить |
| 409 `TOPOLOGY_REVISION_CONFLICT` | Список изменился | Refresh и новое подтверждение |
| 409 `CATEGORY_NOT_EMPTY` | Раздел уже/ещё содержит активные каналы | Показать причину |
| 409 `CHANNEL_KIND_MISMATCH` | TEXT-delete вызван для VOICE или наоборот | Не пытаться автоматически удалить другим endpoint |
| 409 `IDEMPOTENCY_KEY_REUSED` | Тот же ключ с другим намерением | Не выполнять; ошибка состояния клиента |
| 429 `RATE_LIMITED` | Ограничение частоты | Retry-After |
| 503 `PERMISSIONS_UNAVAILABLE` | Нельзя прочитать действующую политику | Не подставлять разрешающие defaults |
| 5xx | Инфраструктурная ошибка | Без false success; сверка результата при возможном commit |

На старых маршрутах прежний общий `409 CONFLICT` не переименовывается без миграции контракта. Новый клиент должен корректно понимать его, если часть команд ещё использует legacy adapters.

## 11. Обновление разрешений и topology на клиентах

### 11.1. Раздельные состояния

У клиента есть отдельные `PermissionStore` и `TopologyStore`. PermissionStore содержит account identity, role, permissions_revision, полный набор grants, состояние загрузки и поколение текущей сессии. Он не хранит административный dirty-draft. Топология содержит собственную revision, категории и каналы. Эти revision нельзя сравнивать между собой.

На bootstrap после проверки сессии асинхронно загружаются effective permissions и topology. До получения прав controls мутации не показываются как доступные. Не задерживать подключённое media, чтение сообщений или весь shell из-за ошибки permission GET. После logout/смены аккаунта очищаются права, открытые menus, drafts форм и незавершённые UI-actions прошлого аккаунта; их поздние ответы игнорируются.

### 11.2. Realtime hints

Существующий `channel.updated {revision}` сохраняется. Добавить:

| Событие | Получатели | Смысл |
|---|---|---|
| `role.permissions.updated` с `{role:"MEMBER", revision}` | Авторизованные клиенты, поддерживающие фичу | Конфигурация роли изменилась: перечитать собственные права; открытому админ-редактору отметить новый baseline |
| `auth.permissions.invalidated` с пустым payload | Только текущие сессии аккаунта, которому изменили роль | Перечитать собственную роль и effective values даже при неизменной permissions_revision |

События не содержат секретов, шестёрку доверенных клиентом grants или чужие account details. Они являются сигналом invalidation; authoritative state — GET и серверные проверки. Если уже есть эквивалентный адресный account/session hint, переиспользовать его с теми же гарантиями, не публиковать дубль.

Для v1 эти два новых hint могут быть **эфемерными**: не продвигать ими durable replay cursor. Их отсутствие восстанавливается REST на reconnect/focus и периодической проверкой. Отправлять после commit; при rollback не отправлять. Это не обещание gap-free доставки, которой нет в текущем post-commit realtime-контуре `[S2]`, строки 95–101.

### 11.3. Совместимость старых клиентов

Не предполагать, что старый строгий parser пропустит неизвестный `kind`. Предлагается opt-in на существующем `/api/v1/realtime`: параметр `capabilities=role_permissions_v1`. Он не меняет auth, `after` или media credential. Только соединения с этой capability получают два новых типа. На reconnect capability отправляется снова.

Capability — не право доступа: нельзя получить чужой адресный hint её подстановкой. Старый клиент без capability получает прежний набор событий. Пропущенные новые события не должны порождать resync-loop и не меняют его replay cursor. Новая schema и классификация ephemeral/durable изменяются одновременно в Go, Vue и Flutter.

### 11.4. Резервное обновление и целевые сроки

Предлагаемые настройки v1:

- GET после login/bootstrap, realtime reconnect и `resync_required`.
- GET по permission hint; одновременно выполняется не больше одного запроса, пачка hints объединяется.
- GET при возврате foreground/focus, если прошлое успешное чтение старше 15 секунд.
- Пока приложение активно — одна проверка каждые 60 секунд, без отдельного таймера в каждом компоненте.
- В фоне периодический timer остановлен. При возвращении он восстанавливается.
- Любой `403 PERMISSION_DENIED` инициирует refresh; он не трактуется как logout или voice-revocation.

Целевой проверяемый результат: при исправном соединении и API клиент меняет controls не позднее 2 секунд после получения hint. При потере hint активный клиент восстанавливается не позднее 65 секунд, если контрольный GET отвечает не дольше 5 секунд. Это проектные критерии теста, не измеренная характеристика production и не гарантия для офлайн-устройства. Безопасность от этих сроков не зависит: backend читает актуальную политику при записи.

### 11.5. Права изменились при открытом UI

Открытое меню пересобирается/закрывается. Если тип создания стал запрещён, заполненная форма показывает причину и не переключается молча на другой тип. Пользователь может явно выбрать разрешённый тип, сохранив название. При полном отзыве создание/удаление блокируется, draft остаётся доступным для копирования и закрытия.

Открытый dirty-редактор администратора не заменяется входящим серверным значением без предупреждения. При потере роли администратора submit недоступен сразу после получения актуального server state.

Права на существующие разговоры и чтение не меняются этими шестью галочками. Нельзя после `role.permissions.updated` вызывать общий reset всего приложения, logout или повторный LiveKit join.

## 12. Идемпотентность и неопределённый результат

### 12.1. Почему отдельный ключ

Каждая новая topology mutation получает `client_request_id` UUIDv4. Он создаётся один раз для конкретного намерения. Не путать с серверным `X-Request-ID`: последний различается у разных HTTP-попыток и предназначен для диагностики `[S2]`.

Уникальность receipt: `(actor_id, client_request_id)`, где actor извлечён из сессии. В intent fingerprint входят операция, resource/parent ID, kind, нормализованное имя и подтверждения; `expected_revision` не входит, поскольку это предикат конкурентности, а не другой объект/намерение. После явного refresh и нового подтверждения ту же ещё не выполненную операцию можно повторить с актуальной expected_revision.

### 12.2. Receipt и атомарность

Предлагаемая минимальная таблица `topology_command_receipts`:

| Поле | Смысл |
|---|---|
| `actor_id`, `client_request_id` | Составной уникальный ключ |
| `operation` | CATEGORY_CREATE / TEXT_CHANNEL_CREATE / VOICE_CHANNEL_CREATE / TEXT_CHANNEL_ARCHIVE / VOICE_CHANNEL_CLOSE / CATEGORY_DELETE |
| `intent_hash` | Fingerprint, не raw request body |
| `resource_id`, `resource_type` | Результат команды |
| `result_state`, `topology_revision` | Состояние в момент commit, не обещание его актуальности сейчас |
| `response_status`, `created_at` | Ответ и серверное время |

Изменение topology, receipt и metadata-only audit коммитятся вместе. Для VOICE receipt подтверждает принятие close, а не финализацию SFU. Уникальный конфликт двух одинаковых запросов приводит к одному результату, не к двум каналам. Ошибки валидации/прав/revision без мутации не создают успешную receipt.

В v1 receipt хранится без TTL: topology-команды редки, запись мала и не содержит переписки. Это позволяет избежать повторного создания после долгого сна приложения. Если позднее вводится retention, отдельно нужен контракт срока действия ключа; нельзя молча удалить receipt и принять давний retry как новое создание.

### 12.3. Повторы

| Случай | Результат |
|---|---|
| Тот же actor/key/intent, первая команда завершена | Одна прежняя receipt, без нового audit/revision/rate-limit charge |
| Тот же actor/key, другое имя/тип/target | 409 IDEMPOTENCY_KEY_REUSED |
| Другой actor с тем же UUID | Независимое пространство ключей, нельзя прочитать чужую receipt |
| Канал после создания уже удалили | Вернуть прежний результат, затем refresh показывает отсутствие; не воссоздавать |
| Право на действие отозвано после успешной операции | Новый mutation request получает актуальный отказ; read-receipt собственного действия доступен активному actor |
| Аккаунт blocked/session revoked | И mutation, и receipt-read запрещены по существующим auth-правилам |

`GET /api/v1/topology-commands/{clientRequestID}` возвращает только собственную квитанцию и не создаёт state. Пример:

```json
{
  "client_request_id": "9f954ba6-6cd0-42ca-a504-353ac45cb2e5",
  "operation": "VOICE_CHANNEL_CREATE",
  "status": "SUCCEEDED",
  "topology_revision": 43,
  "result": {
    "resource_type": "VOICE_CHANNEL",
    "resource_id": "20160d30-9eef-42f6-94ad-cf7a813119dd",
    "state_at_commit": "ACTIVE"
  }
}
```

После timeout receipt 404 не доказывает отсутствие ещё выполняющегося transaction. Клиент повторяет тот же mutation/key с backoff или предлагает «Проверить результат». Новый ключ разрешён только для явно нового намерения, не при транспортной неопределённости.

Если пользователь изменил имя/тип после доказанного 400/403 без commit, при следующем submit создаётся новый key. Черновик не меняется во время неизвестного исхода. Восстановление после закрытия модального окна живёт в app-scoped controller, а не в unmounted component.

## 13. Конкурентность, авторизация и жизненный цикл

### 13.1. Линеаризация изменения прав

Требуемая семантика: **операция, прошедшая защищённую проверку до изменения политики, может завершиться; изменение политики не откатывает уже принятую операцию. После commit новой политики новая защищённая операция не использует старое разрешение.** Порядок появления ответов в сети не определяет порядок commit.

Недостаточно проверить permission только в middleware, затем ждать topology lock и писать по устаревшему grant.

Предлагаемая реализация: один transaction-scoped authorization fence, общий для новой политики и операций, которые зависят от неё. Он может быть построен на транзакционных advisory locks PostgreSQL; shared/exclusive варианты описаны в `[E5]`. Ключ выделяется из существующего реестра блокировок проекта, не из пользовательских ID.

```text
Topology mutation (shared fence):
  BEGIN
  acquire authorization shared fence
  повторно прочитать действительную сессию, аккаунт, текущую роль и policy
  проверить конкретное permission
  выполнить текущие topology/voice locks в существующем порядке
  проверить target/revision/idempotency
  записать mutation + receipt + audit
  COMMIT

Policy update (exclusive fence):
  BEGIN
  acquire authorization exclusive fence
  повторно проверить действующего ADMINISTRATOR
  проверить expected policy revision и новое подтверждение delete
  записать policy + revision + audit
  COMMIT
```

Под тот же exclusive fence включить существующие команды изменения роли/блокировки аккаунта и authority-changing recovery/reset/logout, когда они конкурируют с этими topology mutations. Это обёртка согласования доступа, а не изменение их продуктовой семантики. Нельзя брать shared, а затем повышать его до exclusive внутри той же операции. Fence всегда берётся **до** существующих admin/account/voice/topology locks. Сначала описать фактический lock order и проверить race-тестами; не добавлять произвольный lock посреди текущей цепочки.

Всем обычным HTTP-read, сообщениям, WebRTC и heartbeat этот fence не нужен. Ни одна блокировка не удерживается во время сети LiveKit, публикации WS или пользовательского ожидания. Если existing administration transaction guard обеспечивает тот же порядок и семантику, использовать его вместо второго параллельного механизма и зафиксировать соответствие в ADR.

### 13.2. Топологические гонки

Append-create проверяет target и конечную позицию под существующим topology lock. Удаление категории и создание в ней сериализуются: либо создание первым, и delete видит непустоту; либо delete первым, и create получает CATEGORY_UNAVAILABLE. Reorder/rename/move продолжают использовать expected_revision. Старые admin adapters участвуют в тех же locks; их нельзя оставить обходным путём.

Два удаления одного TEXT не должны создавать два audit/revision. С одним key действует receipt. С разными key второй запрос получает отсутствие/конфликт и refresh, а не повторный «свой успех». Для уже CLOSING VOICE новая команда не добавляет второй набор SFU-removal задач: показать текущее состояние/конфликт; тот же key возвращает прежнюю acceptance receipt.

### 13.3. Гонки с историей и файлами

При archive одновременно с send/edit/upload сервер повторяет условия current TEXT в финальной записывающей операции. Если archive уже принят первым, новое сообщение/привязка отклоняется. Если сообщение закоммичено первым, оно остаётся в сохраняемой архивной истории. Транспортный retry не создаёт вторую запись. Данная фича не меняет существующие DM ACL, attachment URL safety и правила физической уборки.

### 13.4. VOICE и отзыв роли

После принятого close процесс выполняется worker даже если инициатор вышел, потерял role или право voice.delete. Отмена разрешения на удаление не открывает канал обратно. Начатое закрытие не отменяется новой кнопкой. Только администраторская эксплуатационная диагностика может разбирать зависший SFU state; пользовательский интерфейс не вызывает RoomService напрямую.

## 14. Frontend и Flutter: модули и управление состоянием

### 14.1. Общая декомпозиция

| Модуль | Обязанность | Не должен делать |
|---|---|---|
| PermissionStore / PermissionController | Effective snapshot, refresh, session generation, readiness | Хранить admin draft; сбрасывать голос |
| RolePermissionEditor | baseline/draft/revision, diff, подтверждение delete-grants | Менять настройки по одному click без Save |
| TopologyActionResolver | Чистая функция: actor capabilities + target state → набор действий | HTTP, копия truth, выдача владельцу extra-права |
| ContextMenu/ActionSheet | Представление действий, anchor/focus/keyboard | Своя permission-логика |
| TopologyMutationController | Payload/key, submit/reconcile, status, topology refresh | Создавать новый key на timeout |
| CreateChannel/CreateCategory | Поля и client validation | Подключать media или менять роль |
| ConfirmDelete | Контекст/последствия/явное подтверждение | Объявлять SFU финализацию по HTTP acceptance |
| AdminRolesPermissionsView | Компоновка двух ролей и редактора | Доступ MEMBER на основании channel.delete |

Web может использовать Pinia/composables; Flutter — текущие контроллеры/нотификаторы. Имена новых файлов проектные. Не требуется переписывать весь AppState; нельзя просто добавить ещё сотни строк permission/меню/HTTP прямо в один общий state-класс.

### 14.2. Единый resolver

Пример входа без привязки к UI-библиотеке:

```text
resolveActions(
  principal = { role, permissions, readiness },
  context = LIST | CATEGORY(id) | CHANNEL(id),
  topology = currentSnapshot
) -> [{ id, label, visible, enabled, reason, intent }]
```

Action IDs: `create-channel`, `create-category`, `delete-text-channel`, `close-voice-channel`, `delete-category`, плюс существующие административные actions. `intent` содержит ID контекста, а не индекс строки. Resolver одинаково вызывается для ПКМ, «⋯», global «+» и touch. Кнопка «+» у раздела открывает form напрямую через тот же intent; она не обязана открывать меню.

Сервер выдаёт grants, frontend вычисляет presentation. Нельзя передавать `enabled:true` из UI как основание backend. Отсутствующее/неизвестное право интерпретируется как неразрешённое. Политика трёх delete/grants не наследуется из любых административных actions.

### 14.3. Account isolation и запросы

Каждый async callback проверяет session generation и request sequence. Более старый GET permissions не перезаписывает более свежий. При той же permissions_revision смена роли всё равно обновляет effective state. Кэш не переносится между аккаунтами и origin.

Использовать single-flight refresh: одно active Promise/Future плюс dirty-флаг для одного последующего чтения. `channel.updated`, HTTP success и reconnect не запускают независимые десятки одинаковых GET. Optimistic изменения политики/топологии не считаются подтверждёнными до server response.

Админский dirty-state и полученные внешние изменения разделены. После background/resume не терять черновик; после logout он удаляется. Начальная ошибка permission GET не превращает MEMBER в администратора и не открывает controls исходными defaults.

## 15. Безопасность, журнал и ограничения

### 15.1. Необходные барьеры

Каждый server action валидирует активную сессию, текущую роль/permission и объект. Прямой вызов API в обход меню не меняет решение. Member с all=true по-прежнему не меняет policy/role, не переименовывает чужие объекты и не читает чужие DM. Уже действующие CSRF/Origin, body size, HTTPS, session handling сохраняются.

Не добавлять role/permission в редактируемую cookie, localStorage или client-only JWT как источник права. UI может временно иметь старое представление; запись всё равно принимает актуальное server решение. Нельзя доверять полю resource_type вместо реального channel.kind. Кнопка подтверждения — защита от случайности, не защита от злонамеренного авторизованного пользователя.

### 15.2. Ограничение частоты — предлагаемые параметры

Использовать существующий механизм bounded per-source limiting проекта как основу, но для разрешённых topology commands ключом сделать account ID, не только IP. Предлагаемый старт: для MEMBER **10 новых create-команд за фиксированное окно 60 секунд**, суммарно category/TEXT/VOICE; отдельно **10 delete/close за такое же окно**. Это технические параметры deployment, не новые галочки роли. При 429 отдаётся Retry-After. Успешный exact retry по receipt не расходует лимит повторно; невалидные/неавторизованные запросы ограничиваются существующей anti-abuse защитой.

ADMINISTRATOR не ограничивается этим бизнес-лимитом MEMBER, но не обходит общий ingress/abuse limiter. Границы fixed-window и возможный burst на стыке окон тестируются; не объявлять его строгим sliding-window лимитом. Если deployment multi-instance, shared account limiter требует отдельного решения; здесь не обещается распределённая точность process-local счётчика и не добавляется Redis без необходимости.

Лимит частоты не ограничивает итоговое число каналов. Согласованная модель разрешает постепенное накопление. В v1 администратор управляет этим выключением create и обычными административными действиями. Общую квоту/антиспам для свободной регистрации можно развивать отдельно; она не должна появиться скрытой персональной квотой «своих каналов».

### 15.3. Аудит

В транзакции фиксировать actor, operation, target type/ID, server time, request ID и безопасные данные результата. Для policy change — role MEMBER, old/new revision и diff только шести boolean. Историю сообщений, содержимое файлов, секреты и raw request bodies не включать.

В текущем audit API metadata JSON намеренно не публикуется `[S2]`, строка 23. Для нового экрана журнала добавить **явную allowlisted projection** permission diff, а не открыть всё `audit_events.metadata`:

```json
{
  "event_type": "role.permissions.changed",
  "target_role": "MEMBER",
  "changes": [
    { "permission": "channel.voice.delete", "before": false, "after": true }
  ],
  "old_revision": 12,
  "new_revision": 13
}
```

Этот fragment встраивается в типизированный safe audit DTO после проверки совместимости старых clients. UI показывает: **«Администратор изменил права роли “Пользователь”: удалять голосовые каналы — разрешено»**. Имена акторов берутся существующим безопасным способом; вместо технического UUID — human-readable label/fallback. Повтор receipt не порождает новый event об изменении. Отказы могут учитываться в диагностике отдельно, не как успешная мутация.

### 15.4. Метрики и производительность

Достаточны агрегаты количества/ошибок операций, policy update conflicts, time-to-response и pending VOICE closures. Labels ограничены operation/kind/result; account/channel/request IDs не добавляются в time-series labels. Не вводить весь OTel-stack ради этой фичи.

Чтение шести permission не вызывает LiveKit и не делает network call в handler. Permission GET не должен считать roster или участников гильдии. При 100 активных экземплярах клиента polling раз в 60 секунд даёт в среднем около 1,7 GET/с — расчёт для оценки, не фактический benchmark. Следует измерить lock wait и request latency на стенде с одновременной топологией/политикой; неоправданное глобальное блокирование чата недопустимо.

## 16. Миграция, обратная совместимость и выпуск

### 16.1. Подготовка

До изменений записать commit SHA рабочего checkout и найти реальные реализации: role/session guards, admin topology routes, create/rename/move/order/delete leaves, existing locks, validators имён, schema channels/categories, realtime parser и policy отсутствующих полей в старых клиентах. Сопоставление приложить к PR. Это не новый продуктовый вопрос и не повод менять согласованные шесть permissions.

Особенно проверить: сохраняет ли delete-empty архивные category references; существует ли name uniqueness; какие UI-компоненты уже используют общий action menu; как admin UI показывает ошибки и какой lifetime у Flutter voice controller. Не копировать старые ссылки на файлы как подтверждение текущего устройства кода.

### 16.2. Additive migrations

Добавить policy storage и initial MEMBER row; receipt storage и индексы; при необходимости category tombstone. Существующие users/roles/channel kind не менять и не пересоздавать. Archive history не удалять. API не применяет миграции при запуске — использовать существующий отдельный migration step `[S3]`.

Миграции версионированные, up-only по принятому процессу. Повторный запуск/деплой не переустанавливает defaults. При возврате к старому совместимому binary новые таблицы и сохранённая policy остаются; destructively откатывать данные не требуется. Старый бинарник может снова предоставлять topology mutations только администраторам — это временная потеря новой возможности, а не причина стирать сохранённые разрешения.

### 16.3. Порядок публикации

1. **Backend и contracts:** additive migration, новые endpoints, общая авторизация, idempotency, capability-filtered hints. Старые `/admin/*` всё ещё admin-only.
2. **Проверка настроек:** в редакторе видно MEMBER create=true/delete=false. Проверяется, что прежние admin tools не потеряли права.
3. **Web:** общий resolver, menus/forms, admin permissions, account-safe refresh.
4. **Flutter:** тот же контракт для iOS/Android/Windows/macOS; сборка и устройство проверяются отдельно для каждой поддерживаемой платформы.
5. **Staging acceptance и production smoke:** новая/старая версия клиента, изменённые permissions и реальное закрытие VOICE.

Публикация backend с исходными create=true уже делает новые create endpoints доступными активным MEMBER, даже если UI ещё не доставлен. Это ожидаемый эффект согласованных defaults. Не вводить скрытый false-feature-flag, который делает галочку true недействующей. Перед rollout администратор должен понимать это изменение; сначала проверить на staging. При необходимости задержать открытие продакшна сам release держится до готовности, а не выдаётся за включённую функцию.

Новый клиент против старого backend при 404 permission endpoint: новая функция недоступна, другие функции не ломаются; existing admin UI остаётся прежним, новый permission-editor сообщает об отсутствии поддержки сервера. Нельзя подставлять MEMBER defaults и отправлять в старые admin endpoints.

### 16.4. Проверка смешанных версий

Старые native/web не обязаны получить кнопки создания без обновления приложения. Но серверная политика действует независимо от их UI, legacy admin paths не открываются MEMBER, новый event не разрывает старый WS. Изменения политики не требуют разлогинивания пользователей.

Rollback новой web/native версии не должен перезаписывать policy; rollback backend должен быть совместим с schema и category tombstones. Если старый binary не знает tombstones и начнёт показывать удалённые категории, такой rollback несовместим: заранее подготовить совместимый предшествующий binary/reader. Не объявлять additive column автоматически достаточным доказательством semantic rollback-совместимости.

## 20. Definition of Done

Фича считается готовой, когда одновременно выполнены следующие условия:

1. Две роли и шесть независимых permissions реализованы; MEMBER defaults — create=true/delete=false; admin preset неизменяем.
2. Администратор реально меняет MEMBER-policy в админке: warning, explicit Save, defaults-to-draft, conflicts, lost response и безопасный audit работают.
3. Все новые mutations проверяют реальные current permissions; legacy admin endpoints не открыты MEMBER. Сохранены последние active admin и существующие privacy-инварианты.
4. Глобальный «+», «+» у раздела, ПКМ, «⋯» и touch ведут к общим сценариям, без скрытых уникальных функций и unintended join/navigation.
5. Создание/удаление устойчивы к повтору, потерянному ответу, смене роли и конкурентным изменениям. Повтор одного намерения не создаёт новый объект.
6. TEXT archive не уничтожает историю; удаление раздела не каскадирует архив; VOICE закрывается через подтверждённую state machine, а не таймер UI.
7. Новые права применяются без login/reload; серверная безопасность не зависит от доставки hint; старые клиенты не сломаны новыми событиями.
8. Web и заявленные native-платформы прошли релевантные испытания. Если iOS/device build ещё недоступен, объём честно отмечен как частично принятый, а не весь V1 PASS.
9. Миграция не сбрасывает настройки, rollback семантически совместим, документы/schema/backlog/evidence обновлены.

**Главный happy path:** администратор включает voice.delete для роли MEMBER и подтверждает область действия → у пользователя без повторного входа появляется «Удалить голосовой канал…» → пользователь вызывает его через ПКМ или ⋯ и подтверждает конкретный канал → сервер проверяет действующее разрешение → канал остаётся CLOSING до реального завершения → исчезает у всех после финализации. Ни создание, ни изменение галочек не дают пользователю дополнительных административных полномочий.
