# Runtime: ресурсы и здоровье BOOHTACORD

Дашборд: [BOOHTACORD Runtime](https://grafana.fa.shaneque.ru/d/boohtacord-runtime).
UID сохранён; обновление — каждые 30 секунд, исходный интервал — последние 6 часов.

## Область измерения

- `prometheus_main`: node-exporter `176.108.242.211:9100`, job `BOOHTA_cloud`.
  CPU, RAM, swap, диск и сеть относятся ко **всему рабочему серверу**. В них входят
  BOOHTACORD и соседние процессы. Это не метрики отдельно взятого контейнера.
- `boohtacord_metrics`: HTTP-метрики приложения и состояние телеметрии на Hetzner.
- Внешняя сеть: `enp3s0`; диск: `vda`; файловая система `/` — `ext4`.
  При переезде или смене устройства обновите эти селекторы и повторите живую проверку.

## На что смотреть

1. CPU выше 70/90%, RAM и диск выше 80/90% подсвечиваются жёлтым/красным.
   Это ориентиры внимания, не подтверждённые нагрузочным тестом пределы системы.
2. RAM считается по `MemAvailable`: освобождаемый кэш не считается занятой памятью.
   Свободное место — `filesystem_avail`, без резерва root; отдельно видны inode.
3. Load / vCPU выше 100% указывает на очередь либо ожидание I/O. Рост steal говорит
   об отнятом гипервизором времени. PSI показывает время ожидания CPU, памяти и I/O.
4. Сеть показывает входящий/исходящий трафик без повторного подсчёта Docker-интерфейсов.
   UDP RcvbufErrors входит в InErrors — их нельзя суммировать. Это ошибки хоста,
   а не процент потерь зрителя. Качество стрима проверяется в [трейсах](traces.md).
5. API: последние 5xx и P95/P99, отдельные итоги и маршруты за выбранный период.
   Долгоживущий WebSocket исключён из задержки. P95 подсвечивается после 0.3/1 с,
   доля 5xx — после 1/5%. При малом трафике квантили приблизительны.

«Доступен» означает успешный scrape node-exporter, а «3 из 3» — три компонента
телеметрии; ни один показатель не доказывает работоспособность всех функций сайта.
Пропуски метрик остаются «Нет данных». CPU/RAM/диск скрываются при недоступном
экспортере. Графики прошлого периода сохраняют наблюдавшиеся значения.

## Проверка и публикация

```text
python -m unittest discover -s tools/verify/runtime_dashboard -v
python tools/qa/runtime_queries/check_runtime_queries.py docker/observability/dashboards/runtime.json --host-prometheus http://127.0.0.1:9090 --app-prometheus http://127.0.0.1:9091
```

Вторая команда выполняется на Hetzner с приватным доступом к Prometheus. Она
проверяет instant-запросы и час истории графиков, сообщает пустые результаты и
отклоняет ошибки/нечисловые значения. Подстановка rate interval при проверке — 5 минут.
Импортируйте JSON в Grafana с исходным UID, подтвердите обновление существующего
дашборда и проверьте значения/источники в UI. Историю и временной фильтр сохраняйте.
Для секции ресурсов новые агенты, доступ к БД, порты и перезапуск приложения не нужны.

## Пользователи и дневная активность

Секция пользователей требует API с `identity/observe_usage` и миграцией 0043.
`boohtacord_users_registered` — все аккаунты, включая администратора и заблокированных.
`boohtacord_users_registrations{period="today|yesterday"}` — создания по `users.created_at`.
Сутки считаются с 00:00 до 24:00 по Москве (UTC+3), независимо от часового пояса браузера.

`boohtacord_users_daily_active{period="today|yesterday"}` — уникальные аккаунты с успешной
проверкой сессии в этот день. Фоновые авторизованные запросы тоже считаются; это DAU,
не число людей онлайн. Несколько устройств одного аккаунта не увеличивают DAU.
Данные сохраняются в `user_daily_activity` на 32 дня; метки пользователей в Prometheus
не передаются. Первая запись за день ограничена 200 мс, ошибки не мешают авторизации
и видны в `boohtacord_users_activity_write_failures` (сброс при перезапуске API).

Общее число и регистрации доступны сразу. История графиков начинается с включения метрик.
DAU первого дня частичный; сравнение становится доступно после полного предыдущего дня.
Сегодня сравнивается со **всем вчерашним днём**, а не с тем же часом. При вчерашнем DAU=0
абсолютная разница доступна, процент не определён («Нет базы»).

Панели требуют `collection_success=1` и свежий `collected_at_seconds` (не старше 60 с).
Перед агрегацией проверяется свежесть каждой серии; максимум не складывает одинаковые
счётчики нескольких экземпляров API. Отсутствие/ошибка измерений не изображается нулём пользователей.
