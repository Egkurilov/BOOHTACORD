# POC-01: операторский запуск реального захвата игры

Этот документ превращает краткий протокол из [MEDIA_PROTOTYPE.md](../MEDIA_PROTOTYPE.md) в воспроизводимый запуск. Он не меняет требования продукта и не является доказательством сам по себе.

## Что закрывает POC-01

Нужны два самостоятельных прогона: один с презентером на Windows, второй с презентером на Apple-Silicon macOS. В каждом прогоне физический наблюдатель на отдельной машине должен одновременно подтвердить:

- движущееся изображение реальной игры;
- именно звук этой игры, а не только звук вкладки или наличие аудиодорожки;
- речь презентера в голосовом канале;
- отсутствие устойчивой цифровой петли (`sustained digital loop`), возвращающей собеседнику его же воспроизведение.

Зелёный `/api/v1/health`, наличие LiveKit-дорожки, скриншот picker, tab-only audio, unit-тест или эмулятор не закрывают этот POC. Он также не измеряет 720p/1080p, FPS, bitrate, RTT, loss или вместимость: это отдельный POC-02 и нагрузочный gate.

## Прежде чем приглашать участников

1. Владелец сервера в своём защищённом терминале выполняет начальный bootstrap администратора по [ADMIN_OPERATIONS.md](administrator.md). Пароль не передают в чат, не помещают в командную строку, логи, evidence или репозиторий. До bootstrap публичная форма регистрации корректно показывает недоступность регистрации; это не повод создавать первого администратора через UI.
2. Откройте публичный HTTPS-адрес deployment. Гостевой `GET /api/v1/auth/session` должен возвращать понятный неаутентифицированный результат, а не использовать `401` как экран загрузки. Защищённые ресурсы без сессии по-прежнему обязаны отвечать `401`.
3. Администратор входит через заглавную страницу. Зарегистрируйте отдельные аккаунты презентера и наблюдателя только после bootstrap. Не используйте один аккаунт на обеих машинах: у аккаунта может быть лишь одно активное голосовое подключение.
4. Подготовьте одну категорию и один открытый `VOICE`-канал. Пока отдельный UI управления топологией не является частью этого экрана, администратор может сделать контролируемую разовую настройку в DevTools Console **на том же HTTPS-origin**. Код ниже использует текущую HTTP-only сессию, не содержит пароль или токен и намеренно прекращает работу при любой ошибке:

```js
async function postJson(path, body) {
  const response = await fetch(path, {
    method: 'POST',
    credentials: 'same-origin',
    headers: { accept: 'application/json', 'content-type': 'application/json' },
    body: JSON.stringify(body),
  })
  if (!response.ok) throw new Error(`${path}: HTTP ${response.status} ${await response.text()}`)
  return response.json()
}

const category = await postJson('/api/v1/admin/categories', { name: 'POC' })
const voiceChannel = await postJson(`/api/v1/admin/categories/${encodeURIComponent(category.id)}/channels`, {
  name: 'game-audio-poc',
  kind: 'VOICE',
})
console.log({ categoryId: category.id, voiceChannelId: voiceChannel.id })
```

Не вставляйте в evidence текст HTTP-ошибки, если в нём могут быть персональные данные. Если категория или канал уже существуют, используйте их и не создавайте дубликаты.

## Оборудование и сведения для записи

Для каждого прогона зафиксируйте в отдельной JSON-записи:

- тип машины и архитектуру презентера; для macOS — Apple Silicon, а не Intel;
- версию ОС и Chrome Stable;
- используемые микрофон и устройство вывода без серийных номеров;
- образ/digest LiveKit на deployment, название игры и выбранный источник capture;
- идентификатор отдельной physical observer machine и имя наблюдателя в поле `observer`;
- время начала/окончания и путь к каждому не содержащему секретов артефакту.

Презентер и наблюдатель используют наушники. Это исключает акустическую обратную связь и делает наблюдение цифровой петли осмысленным. Наблюдатель — реальный человек за отдельной физической машиной; вторая вкладка на той же машине, headless-клиент или запись без человека не подходит.

## Сценарий: выполнить отдельно для Windows и Apple-Silicon macOS

1. Презентер и наблюдатель входят под разными аккаунтами, видят один `VOICE`-канал и входят в него. Каждый выбирает корректные устройства ввода/вывода. Презентер даёт браузеру разрешение на микрофон только в момент явного входа в голос.
2. Презентер запускает реальную игру, в которой есть узнаваемый непрерывный или повторяемый звук и заметное движение. До начала захвата запишите игру и её событие со звуком в evidence.
3. Презентер запускает демонстрацию через системный browser picker. Если отдельное окно игры недоступно, разрешён захват всего экрана с явным предупреждением о лишнем содержимом; это надо записать как `capture_source`. Нельзя вместо этого подменять сценарий desktop-клиентом, драйвером, virtual cable или звуком одной вкладки.
4. Наблюдатель выбирает именно этот remote screen stream. В течение не менее 10 секунд он подтверждает, что изображение меняется синхронно с действиями в игре, а не показывает статичный кадр или preview презентера.
5. Наблюдатель подтверждает отдельное событие игрового звука, которое происходит при нём в игре. Затем презентер произносит короткую контрольную фразу; наблюдатель подтверждает, что услышал речь из голосового канала отдельно от игрового аудио.
6. Выполните проверку петли в наушниках: наблюдатель один раз произносит короткую контрольную фразу, затем замолкает минимум на 15 секунд; презентер подтверждает, что услышал её один раз, без повторяющегося или нарастающего возврата. После этого наблюдатель выключает свой микрофон и ещё раз подтверждает получение игры и речи презентера. Если различить цифровую петлю и локальную акустику нельзя, прогон недействителен и должен быть `BLOCKED`, а не `PASS`.
7. Пока слышны игра и речь, зритель меняет **громкость только презентера** последовательно на 0%, 175% и 200%. На 0% голос презентера исчезает, звук игры сохраняется; на 175% и 200% голос возвращается с наблюдаемым изменением уровня. Запишите каждое наблюдение отдельно. При новом аудиотреке/переподключении выбранный уровень должен примениться снова.
8. Зритель выключает звук **выбранной трансляции**: игра становится неслышной, голос презентера остаётся. Затем включает его и слышит новое игровое событие. Если доступен второй stream, переключитесь на него и обратно, повторите включение; иначе отметьте `screen_switch_and_reenable` как `NOT_RUN`, не выдавая эту часть QA-06 за PASS.
9. Презентер останавливает демонстрацию штатной кнопкой приложения или системной кнопкой браузера и фиксирует результат. Это не доказывает POC-03, но предотвращает неявное продолжение теста на старой дорожке.

Полностью повторите шаги 1–9 при презентере на второй ОС. Windows может быть observer machine для macOS-прогона и наоборот, если во время каждого прогона это отдельные физические машины и участники используют разные аккаунты.

## Как классифицировать результат

Создайте одну запись из [templates/evidence.json](../../templates/evidence.json) для каждой попытки, например `poc-01-windows-YYYY-MM-DD-001.json` и `poc-01-macos-apple-silicon-YYYY-MM-DD-001.json`. Сами JSON-записи и медиа не коммитятся автоматически; сохраните их и артефакты в защищённом месте. Не записывайте пароли, session/media tokens, DM, текст сообщений или личные данные в `notes` и артефакты.

| Статус | Когда ставить |
| --- | --- |
| `PASS` | В конкретном прогоне named physical observer подтвердил движение игры, её звук, голос и отсутствие устойчивой цифровой петли; заполнены окружение, observer, timestamp и пути к артефактам. POC-01 закрыт только после двух `PASS`: Windows и Apple-Silicon macOS. |
| `FAIL` | Все необходимые условия были доступны, но хотя бы ожидаемый наблюдаемый результат не произошёл: например, наблюдатель не слышит звук игры или слышит устойчивую петлю. Укажите конкретное ожидание и фактическое наблюдение. |
| `BLOCKED` | Внешняя предпосылка не позволяет честно выполнить сценарий: нет второй physical observer машины, на нужной ОС Chrome/picker не даёт источник с игровым звуком, нет bootstrap/канала, или нельзя исключить акустическую петлю. Не заменяйте blocked-сценарий драйвером, virtual cable, tab-only audio или иной платформой. |
| `NOT_RUN` | Прогон ещё не запускался. Это не является частичным PASS. |

При проблеме с конкретным игровым окном сначала попробуйте позволенный browser picker захват всего экрана и честно отметьте это. Если и тогда не выполнены изображение реальной игры и game audio, оставьте `BLOCKED`; не меняйте продуктовую платформу ради прохождения.

## Артефакты и итог

Для `PASS` укажите как минимум сохранённые вне репозитория: снимок/короткую запись с observer machine с движущейся игрой, отметку отдельного игрового звукового события, отметки контрольной речи и проверки петли, а также версию браузера и digest LiveKit. Артефакты могут содержать игровое изображение, но не должны содержать секреты или чужие личные сообщения.

После двух проходов обновите release evidence только фактическими результатами. Один успешный Windows-прогон, один доступный LiveKit track или заполненный шаблон не позволяют заявлять поддержку Windows/macOS, игрового аудио или capacity profile.

Проверьте полноту двух записей командой `powershell -ExecutionPolicy Bypass -File tools/verify/poc_01_evidence/verify-poc-01-evidence.ps1 -WindowsEvidence <windows-record> -MacEvidence <macos-arm64-record>`. В записи macOS укажите `presenter_architecture: arm64`. Успех валидатора подтверждает структуру записей и четыре наблюдения POC-01, но не подменяет решение физического наблюдателя и не проверяет дополнительные `qa06_audio_controls`. QA-06 закрывайте только после самостоятельного подтверждения этих полей на двух клиентах.
